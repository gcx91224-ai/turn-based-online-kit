# 11 · 排位与匹配

排位是"让陌生人也能找到对手"的机制。它比好友复杂，因为涉及三件容易做错的事：
**怎么配、分怎么算、谁说了算**。

---

## 一、分数模型：先选一个能解释的

### 固定 ±10（推荐起步）

```
初始 1200，赢 +10，输 −10，平局不动
```

- ✅ 玩家一看就懂："再赢三把上 1230"
- ✅ 实现只有几行，不会有公式 bug
- ✅ 分数变化可预期，不会出现"赢了只加 2 分"的挫败
- ❌ 强者虐菜也能稳定上分（炸鱼）
- ❌ 分数不收敛，长期会通胀

### Elo / Glicko

```
期望胜率 E = 1 / (1 + 10^((对手分-我的分)/400))
新分 = 旧分 + K × (实际结果 - 期望)
```

- ✅ 赢强者加得多、赢弱者加得少，长期收敛
- ❌ 玩家看不懂"为什么我只加了 3 分"
- ❌ K 值、初始分、定级赛都要调，调不好体验更差

**建议**：先固定 ±10 跑一段时间，有真实对局数据再考虑 Elo。
过早引入 Elo 的典型后果是：玩家觉得"赢了不加分"，而你还在怀疑是不是有 bug。

## 二、匹配队列

### 为什么单独一个全局 DO

队列是**跨房间**的：所有在等的人必须放在同一个地方才能互相看见。

```jsonc
"durable_objects": {
  "bindings": [
    { "name": "ROOMS", "class_name": "Room" },
    { "name": "LADDER", "class_name": "Ladder" }   // 全局单例
  ]
},
"migrations": [
  { "tag": "v1", "new_sqlite_classes": ["Room"] },
  { "tag": "v2", "new_sqlite_classes": ["Ladder"] }
]
```

```js
env.LADDER.get(env.LADDER.idFromName('__ladder__'))   // 固定名字 = 全世界只有一个
```

单个 DO 串行处理所有排队请求，天然不需要锁。朋友局规模完全够用；
真要几万人同时匹配，再按分数段分片（`__ladder_1200__`、`__ladder_1300__`）。

### 撮合算法

```js
const NEAR = 300;             // 基础分差上限
const WIDE_AFTER_MS = 20000;  // 等超过 20 秒就放宽
const WIDE = 600;
const EXPIRE_MS = 90000;      // 等超过 90 秒自动退出
```

每次有人进出队列，就尝试撮合：

```js
for (let i = 0; i < queue.length; i++) {
  for (let j = i + 1; j < queue.length; j++) {
    const gap = Math.abs(queue[i].r - queue[j].r);
    const waited = now - Math.min(queue[i].at, queue[j].at);
    const limit = waited > WIDE_AFTER_MS ? WIDE : NEAR;
    if (gap > limit) continue;
    // 分差最小优先；一样近，先配等得久的
  }
}
```

三个设计点：

1. **窗口随等待时间放宽**：不然高分段的人永远配不上。
2. **分差最小优先**，而不是"先来先配"：体验上"配到一个水平接近的"比"配得快"更重要。
3. **撮合后立刻从队列里摘掉**，并且**用摘下来的对象发消息** —— 不要拿 token 回去查队列，
   人已经不在队列里了，查不到就等于"配上了但谁都不知道"。

### ★ 匹配成功后，不要新建一套对局

```
匹配成功 → 生成一个普通房间码 → 两边各自进那间房
```

这样房间、座位、回合计时、断线重连、观战（如果有）全都复用，
排位只是"帮你们找到彼此"，不是"另一套游戏"。

```js
tell(a, { type: 'matched', code, side: 'host',  opp: { name: b.name, r: b.r } });
tell(b, { type: 'matched', code, side: 'guest', opp: { name: a.name, r: a.r } });
```

客户端收到就 `location.href = '/r/' + code`，和手动邀请走同一条路径。

### 队列要能重连

排队期间客户端什么都不发，空闲的 WebSocket 会被中间设备掐掉。必须：

- 客户端每 20-25 秒 `ping`
- 断线自动重连 + 重新入队（同一 token 覆盖旧条目）
- 服务端清理"socket 已经没了"和"等太久"的条目

**队列持久化只存人，不存 socket**：

```js
async persist() {
  const bare = queue.map(q => ({ token: q.token, name: q.name, r: q.r, at: q.at }));
  await this.ctx.storage.put('queue', bare);   // socket 不能序列化
}
```

DO 重启后，那些没有 socket 的条目会在下一次清理时被摘掉。

## 三、结算归属：整件事里最容易错的部分

### 情况 A：服务器算胜负（权威模型）

简单：房间结束时服务器知道赢家，直接写分。

```js
if (this.config.ranked && !this.settled) {
  this.settled = true;
  await players.applyResult(winnerToken, won);
}
```

只需要注意**幂等**：一局只结算一次。用 `settled` 标记。

### 情况 B：客户端上报（锁步模型）

如果服务器不懂规则（见 [01](01-architecture.md)），它不知道谁赢了，只能等客户端上报。
这时会冒出一整串问题：

#### ① 两端都要报，而且必须一致

```js
if (!seats.every(id => reports[id] != null)) return;      // 还没齐
if (!seats.every(id => reports[id] === reports[0])) return; // 报的不一致
```

只信一份，可能被单方面篡改；两份不一致，说明至少一方有问题 —— **宁可这一局不算分**。

#### ② 有人掉线/慢报怎么办

死等会让"打完了分没动"变成常态。策略：

```
缺一方 → 先催他补报
      → 催不到，且他确实不在线 → 按收到的那一份算
      → 他还在线只是慢 → 再等 8 秒 × 3 轮
```

**注意这里的作弊窗口**：如果对面还在线，就先按我这份算，我可以"抢分"。
所以顺序必须是：先确认对面真的不在线，才允许单边结算。

#### ③ 身份必须互不相同

真实踩过的 bug：

```
两个座位解析成了同一个 token
→ 同一个人被先 +10 再 −10
→ 分数看起来没动，用户报"我赢了但不加分"
```

```js
const seen = {};
for (const seat of seats) {
  const tk = reportTokens[seat];
  if (seen[tk]) return;          // 同一人占了两个座位，这局不算
  seen[tk] = true;
}
```

#### ④ 静默失败是最难查的 bug

```js
if (!config.ranked) return;      // ❌ 用户只看到"分没动"
```

改成每一处提前返回都广播原因：

```js
const why = (t) => broadcast({ type: 'notice', text: '结算：' + t });
if (!config.ranked) return why('这间房不是排位房');
if (this.settled) return why('这一局已经结算过');
```

上线后你会发现，**80% 的"分数没动"靠这一句话就能定位**。

#### ⑤ 写分只认账号 token

座位令牌是每局新生成的，拿它写分，榜单上就会出现一批"打一局就消失"的幽灵号。
写分接口必须收 `{ token: 账号token, won }`，查不到身份就跳过，不要凭空建档。

> 凭空建档还有一个变体：`if (!profile) create({ name: '玩家' })`。
> 名字都懒得填的那种，最后榜单上全是"玩家"。

## 四、排行榜

```js
ladder(top = 50) {
  return Object.entries(players)
    .filter(([, p]) => p.rate && p.rate.games >= MIN_GAMES)   // 打够场次才上榜
    .sort((a, b) => b[1].rate.r - a[1].rate.r)
    .slice(0, top)
    .map(([token, p]) => ({
      id: token.slice(0, 8),      // ★ 只给短号
      name: p.name,
      avatar: p.avatar,
      r: p.rate.r,
      w: p.rate.w,
      l: p.rate.l
    }));
}
```

三个要点：

1. **门槛**（比如 ≥10 局）：否则赢一把就上榜首。
2. **脱敏**：返回短号，永远不返回 token。
3. **排序要稳定**：同分时按场次/胜率再排，否则榜单每次刷新都在跳。

排行榜是读多写少的，可以加缓存（DO 内存里存 5 秒），但朋友局没必要。

## 五、防刷分：做不做，取决于给谁玩

| 场景 | 建议 |
|---|---|
| 只给朋友玩 | **不做**。固定 ±10 + 不限制，最省事，也没人刷 |
| 公开链接、有人认真玩 | 至少做"同对手冷却"（30 分钟内同一对只算一次） |
| 有奖励/赛季 | 必须做：同对手冷却 + 同设备检测 + 异常分数监控 |

一个真实取舍：这个套件的参考项目上线时**明确选择不做防刷分**，
因为用户就是和朋友玩，加限制反而让"连打三把"变得莫名其妙。
代码里连 `pairKey` 都收下了但没用 —— 留着以后要加时不用改接口。

**先把接口留出来**（`applyResult(token, won, pairKey)`），比事后改签名便宜。

## 六、端到端验收清单

这些只能在**线上、两个真人**的环境验，单测覆盖不到：

- [ ] 两个浏览器同时点匹配 → 进同一间房 → 打完 → 分数各 ±10
- [ ] 匹配中刷新页面 → 还能继续匹配/进房
- [ ] 一方关掉页面 → 另一方不会永远卡在"等结算"
- [ ] 同一设备开两个窗口匹配 → 不会自己配到自己
- [ ] 排行榜上分数和"我的分数"一致
- [ ] 榜单里看不到任何完整 token
- [ ] 连打三把，分数是三把的累计（不是只算最后一把）
- [ ] 分数没动时，能从上一条广播消息里看出原因

---

## 小结

排位的复杂度不在算法，在**状态归属**：

- 谁生成身份（客户端 token，不是座位令牌）
- 谁算胜负（服务器优先；不行就让两端报，但要容错）
- 谁写分数（服务器，且幂等）
- 谁看得到什么（榜单只给短号）

把这四个问题回答清楚，剩下的都是几十行代码。
